# F5: 交易系统状态管理

## Findings

### [1] Event sourcing stores every state change as an immutable append-only event; current state is a projection that can be rebuilt to any past moment—giving a complete audit trail for trading systems.
- quote: "Event sourcing is an architectural pattern where state changes are captured as an immutable sequence of events, rather than just storing the current state. Each event represents a fact that happened at a specific point in time, providing a complete audit trail and enabling system reconstruction to any historical point."
- url: https://questdb.com/glossary/event-sourcing/
- source_type: primary
- published: unknown (QuestDB glossary, current 2026)
- confidence: high

### [2] In production trading data platforms, positions are derived queries over the trade/event store ("never a stored guess"), so position memory cannot drift from the order lifecycle history.
- quote: "Positions are not stored guesses; they are derived from the canonical trade store as of a chosen date and book, netted and aggregated, and reconciled back to the blotter"
- url: https://durgaanalytics.com/event_sourcing_audit_trading
- source_type: secondary
- published: unknown (course portal, Prajesh Jha / Gravitas ETRM)
- confidence: medium

### [3] ETRM-grade event-sourced trade cores record every lifecycle change (Captured/Amended/Confirmed/Settled) as immutable events; projections serve position, P&L, and audit read models, and bitemporality (valid-time + transaction-time) is required for point-in-time revaluation.
- quote: "Rather than overwriting rows, every change is recorded as an immutable event in an append-only log, and current state, positions, P&L, the audit view, is a projection derived by replaying those events. This is what gives the platform a perfect audit trail and the ability to reconstruct any state as of any past moment"
- url: https://durgaanalytics.com/event_sourcing_audit_trading
- source_type: secondary
- published: unknown
- confidence: medium

### [4] MiFID II RTS 24 (Commission Delegated Regulation (EU) 2017/580) requires venues to retain every order submission, amendment, cancellation, and execution with chronological lifecycle events so authorities can reconstruct how trades came into existence—not just completed fills.
- quote: "Its primary objective is to ensure regulators can reconstruct market events with precision by preserving comprehensive records of: every order submitted; every amendment made; every cancellation; every execution; the chronological sequence of events (Lifecycle events)."
- url: https://reg-x.co.uk/blogs/mifid-ii-rts-24-annex-iv-order-execution-record-keeping/
- source_type: secondary
- published: 2026-07-01
- confidence: high

### [5] RTS 24 Annex IV treats Section 1 (order intent/lifecycle) and Section 2 (execution results) as one linked record; executions must remain linked to originating orders via unique order IDs—an unbroken chain from submission through amendments and partial fills.
- quote: "Section 1 captures the intent to trade. Section 2 captures the result of that intent. … executions remain linked to their originating orders. This linkage enables investigators to answer questions such as: Which order generated this trade? Was the order amended beforehand?"
- url: https://reg-x.co.uk/blogs/mifid-ii-rts-24-annex-iv-order-execution-record-keeping/
- source_type: secondary
- published: 2026-07-01
- confidence: high

### [6] For algorithmic trading, RTS 24/Annex IV additionally requires retaining algorithm/automated-decision identifiers so supervisors can analyse the behaviour of specific algos—decision provenance is part of the audit trail, not just order fields.
- quote: "Where algorithmic trading is involved, RTS 24 requires trading venues to retain identifiers associated with automated decision making or execution. Capturing these identifiers allows competent authorities to analyse the behaviour of specific algorithms during supervisory investigations."
- url: https://reg-x.co.uk/blogs/mifid-ii-rts-24-annex-iv-order-execution-record-keeping/
- source_type: secondary
- published: 2026-07-01
- confidence: high

### [7] ESMA MiFID II Article 17(2) requires high-frequency algorithmic traders to store accurate, time-sequenced records of all placed orders including cancellations, executed orders, and quotations—and keep strategy/parameter/risk-control descriptions available to competent authorities.
- quote: "An investment firm that engages in a high-frequency algorithmic trading technique shall store in an approved form accurate and time sequenced records of all its placed orders, including cancellations of orders, executed orders and quotations on trading venues and shall make them available to the competent authority upon request."
- url: https://www.esma.europa.eu/publications-and-data/interactive-single-rulebook/mifid-ii/article-17-algorithmic-trading
- source_type: primary
- published: MiFID II Directive 2014/65/EU Art. 17 (text current as of fetch 2026-09)
- confidence: high

### [8] TradingAgents (open-source multi-agent LLM trading framework) persists an always-on decision log to `~/.tradingagents/memory/trading_memory.md`; the next same-ticker run injects recent decisions plus cross-ticker lessons into the Portfolio Manager prompt after computing realized return/alpha and a one-paragraph reflection.
- quote: "The decision log is always on. Each completed run appends its decision to ~/.tradingagents/memory/trading_memory.md. On the next run for the same ticker, TradingAgents fetches the realised return (raw, and alpha against the instrument's regional benchmark), generates a one-paragraph reflection, and injects the most recent same-ticker decisions plus recent cross-ticker lessons into the Portfolio Manager prompt"
- url: https://raw.githubusercontent.com/TauricResearch/TradingAgents/main/README.md
- source_type: primary
- published: v0.5.1 notes 2026-09 (decision-log memory introduced ~v0.2.4 2026-04)
- confidence: high

### [9] TradingAgents treats live holdings as explicit agent context via `PortfolioContext` (cash + positions with quantity/average_price); empty positions ≠ no portfolio, so position memory is a first-class input to trader/risk/PM agents rather than inferred from logs.
- quote: "By default the agents do not know what you hold … Pass a portfolio to have the trader, the risk analysts and the portfolio manager work against your actual book. … An empty positions list means a flat book, which is different from passing nothing. A run without a portfolio is never treated as flat."
- url: https://raw.githubusercontent.com/TauricResearch/TradingAgents/main/README.md
- source_type: primary
- published: portfolio-aware runs in v0.5.0 2026-09
- confidence: high

### [10] FinPos (arXiv:2510.27251, 2025-10-31) formalizes "position-aware trading": agents must maintain continuous position state (no auto-liquidation); returns are position_t × log-price-change; dual agents separate direction from quantity/risk, with per-trade size capped by 95% CVaR.
- quote: "the agent makes a trading decision on each trading day … and explicitly maintains its position state. The agent's decisions no longer involve automatic liquidation; rather, it must consider the continuation and adjustment of current positions … we cap the size of each trade to the maximum suggested by the 95% CVaR."
- url: https://arxiv.org/html/2510.27251v1
- source_type: primary
- published: 2025-10-31
- confidence: high

### [11] FinPos uses hierarchical memory (short/mid/long + reflection layers) with a memory allocator; post-decision reflection migrates repeatedly-valid memories deeper, and the quantity agent must cite supporting memory index IDs in structured JSON output—making decision provenance machine-checkable.
- quote: "The memory module utilizes a memory allocator to distribute the acquired information across memory layers of varying depths … memories that repeatedly prove their validity are gradually migrated into deeper layers … JSON: order_size, summary_reason, short_memory_index, middle_memory_index, long_memory_index, reflection_memory_index, reflection_analysis"
- url: https://arxiv.org/html/2510.27251v1
- source_type: primary
- published: 2025-10-31
- confidence: high

### [12] KTD-Fin (arXiv:2605.28359, 2026-05-27) shows LLM trading evaluation must separate market/style beta from selection alpha (Barra-style attribution) and that pretraining "memory leakage" via real tickers/dates can substitute for live reasoning—decision logs should record anonymized signals vs memorized narrative.
- quote: "long backtests often overlap with the knowledge cutoffs of frontier LLMs, allowing memorized tickers, dates, prices, and market narratives to substitute for investment reasoning … cumulative return is not the same as stock-selection skill"
- url: https://arxiv.org/html/2605.28359v1
- source_type: primary
- published: 2026-05-27
- confidence: high

### [13] KTD-Fin's execution engine always feeds agents account state, current positions, and last-step execution results as observations, and logs all constraint violations and execution outcomes so invalid LLM actions stay visible rather than silently corrected.
- quote: "At each trading step the agent observes account state, current positions, last-step execution results, benchmark-relative performance, and summary constraints … The simulator logs all violations and execution outcomes so invalid LLM actions remain visible rather than being silently corrected."
- url: https://arxiv.org/html/2605.28359v1
- source_type: primary
- published: 2026-05-27
- confidence: high

### [14] The Agentic Trading survey (ESWA / arXiv:2605.19337, 2026-05-19) warns that LLM rationales are not faithful to internal decisions; auditability requires grounded, time-stamped tool calls, data snapshots, and execution logs—and protocol reporting is extremely sparse (only 2/19 primary studies report time-consistent splits; 1/19 explicit cost models; 0/19 reach R3 reproducibility).
- quote: "such text is not guaranteed to be faithful to the true internal decision process. Meaningful auditability therefore depends on grounded, time-stamped tool calls, data snapshots, and execution logs that can be independently verified."
- url: https://arxiv.org/html/2605.19337v1
- source_type: primary
- published: 2026-05-19 (screened through 2026-03-09)
- confidence: high

### [15] Agentic Trading's memory taxonomy for trading agents is Working / Episodic / Semantic; adaptation includes memory consolidation and self-reflection as distinct layers—decision logs and position state map to episodic memory, strategy rules to semantic memory.
- quote: "4 Memory Architecture … 4.1 Working Memory … 4.2 Episodic Memory … 4.3 Semantic Memory … 12.1 Memory Consolidation … 12.3 Self-Reflection"
- url: https://arxiv.org/html/2605.19337v1
- source_type: primary
- published: 2026-05-19
- confidence: medium
