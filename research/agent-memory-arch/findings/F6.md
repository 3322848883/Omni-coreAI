# F6: 上下文工程

## Findings

### [1] 生产级 agent 的头号指标是 KV-cache 命中率：Manus 平均输入:输出 token 比约 100:1，缓存读/写价差可达 10 倍
- quote: "If I had to choose just one metric, I'd argue that the KV-cache hit rate is the single most important metric for a production-stage AI agent... In Manus, for example, the average input-to-output token ratio is around 100:1... with Claude Sonnet, for instance, cached input tokens cost 0.30 USD/MTok, while uncached ones cost 3 USD/MTok—a 10x difference."
- url: https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- source_type: primary
- published: 2025-07-18
- confidence: high

### [2] 前缀稳定性是硬约束：LLM 自回归特性下，前缀任意 1 token 差异会使该 token 之后的缓存全部失效；常见错误是把秒级时间戳放进 system prompt 开头
- quote: "Keep your prompt prefix stable. Due to the autoregressive nature of LLMs, even a single-token difference can invalidate the cache from that token onward. A common mistake is including a timestamp—especially one precise to the second—at the beginning of the system prompt. Sure, it lets the model tell you the current time, but it also kills your cache hit rate."
- url: https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- source_type: primary
- published: 2025-07-18
- confidence: high

### [3] 上下文应 append-only 且序列化确定性；工具集在迭代中途增删会同时打穿 KV-cache 并让模型引用已消失的工具定义
- quote: "Make your context append-only. Avoid modifying previous actions or observations. Ensure your serialization is deterministic. Many programming languages and libraries don't guarantee stable key ordering when serializing JSON objects, which can silently break the cache... unless absolutely necessary, avoid dynamically adding or removing tools mid-iteration... tool definitions live near the front of the context... any change will invalidate the KV-cache for all subsequent actions and observations."
- url: https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- source_type: primary
- published: 2025-07-18
- confidence: high

### [4] DeepSeek 上下文缓存（磁盘 KV）默认对所有用户开启、无需改代码；命中要求与已持久化的 cache prefix unit 完全匹配
- quote: "The DeepSeek API Context Caching on Disk Technology is enabled by default for all users... A subsequent request can only hit the cache if it fully matches a cache prefix unit."
- url: https://api-docs.deepseek.com/guides/kv_cache
- source_type: primary
- published: unknown
- confidence: high

### [5] DeepSeek 前缀持久化发生在三处：请求边界（用户输入末尾/模型输出末尾）、多请求公共前缀检测、长文本固定 token 间隔切块；缓存命中在 usage 里以 prompt_cache_hit_tokens/prompt_cache_miss_tokens 计量
- quote: "Persistence at request boundaries: Each request will produce two cache prefix units at the end position of the user input and the end position of the model output... Common prefix detection persistence... Persistence at fixed token intervals... prompt_cache_hit_tokens: The number of tokens in the input of this request that resulted in a cache hit."
- url: https://api-docs.deepseek.com/guides/kv_cache
- source_type: primary
- published: unknown
- confidence: high

### [7] DeepSeek 磁盘缓存是 best-effort：构建需数秒，闲置后几小时到几天自动清除；只缓存输入前缀，输出仍按 temperature 随机生成
- quote: "The cache system works on a best-effort basis and does not guarantee a 100% cache hit rate. Cache construction takes seconds. Once the cache is no longer in use, it will be automatically cleared, usually within a few hours to a few days. The hard disk cache only matches the prefix part of the user's input."
- url: https://api-docs.deepseek.com/guides/kv_cache
- source_type: primary
- published: unknown
- confidence: high

### [8] OpenAI/Azure OpenAI 前缀缓存门槛：可缓存前缀至少 1024 token 且前 1024 token 完全一致；前 1024 内 1 字符差异即 cache miss（cached_tokens=0）
- quote: "A minimum of 1,024 tokens in length. The first 1,024 tokens in the prompt must be identical... A single character difference in the first 1,024 tokens results in a cache miss, which is characterized by a cached_tokens value of 0."
- url: https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/prompt-caching
- source_type: primary
- published: 2026-08-11
- confidence: high

### [9] OpenAI/Azure OpenAI 缓存粒度与生命周期：GPT-5.5 及更早在 1024 之后按 128-token 增量命中；内存缓存闲置 5–10 分钟常被清除、最迟 1 小时必清；extended retention 最长 24 小时；GPT-5.6+ 起 cache write 收费、默认最小 TTL 30m
- quote: "On GPT-5.5 and earlier models, cache hits after the first 1,024 tokens occur in 128-token increments... The system typically clears caches within 5 to 10 minutes of inactivity and always removes them within one hour of the cache's last use... Extended prompt cache retention keeps cached prefixes active for longer, up to a maximum of 24 hours... cache writes can incur charges in addition to discounted cache reads... The only supported value is 30m"
- url: https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/prompt-caching
- source_type: primary
- published: 2026-08-11
- confidence: high

### [10] OpenAI/Azure OpenAI 上下文组装官方建议：稳定/可复用内容放 prompt 开头，动态内容放末尾，会话上下文 append-only；用 prompt_cache_key 把共享前缀的请求聚到同一 key，高 QPS 时按 key 分片
- quote: "Place stable or repeated content at the beginning of the prompt and dynamic content at the end. Keep conversation context append-only. Reuse a consistent prompt_cache_key for requests that share a prefix. For high-volume workloads, partition traffic across keys while keeping a stable mapping between each key and its prefixes."
- url: https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/prompt-caching
- source_type: primary
- published: 2026-08-11
- confidence: high

### [11] Anthropic 缓存计价：cache write = 基础输入价 1.25×，cache read = 基础输入价 0.1×；长 prompt 场景成本最多降 90%、TTFT 最多降 85%（100K token 书本问答 11.5s→2.4s）
- quote: "Writing to the cache costs 25% more than our base input token price... using cached content is significantly cheaper, costing only 10% of the base input token price... reducing costs by up to 90% and latency by up to 85% for long prompts... Chat with a book (100,000 token cached prompt): 11.5s → 2.4s (-79%), -90% cost"
- url: https://www.anthropic.com/news/prompt-caching
- source_type: primary
- published: 2025-08-14
- confidence: high

### [12] Anthropic 上下文工程原则：把 context 当有限注意力预算（attention budget），目标是「最小高信号 token 集」；系统提示分段（XML/Markdown 小节），工具集保持最小可用，few-shot 用精选多样例而非穷举边界
- quote: "LLMs have an 'attention budget' that they draw on when parsing large volumes of context... good context engineering means finding the smallest possible set of high-signal tokens... organizing prompts into distinct sections (like <background_information>, <instructions>...)... curate a set of diverse, canonical examples... curating a minimal viable set of tools"
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: primary
- published: 2025-09-29
- confidence: high

### [13] 长时运行 agent 的三种上下文扩展手段：compaction（临近上限时摘要后重启窗口，Claude Code 保留架构决策/未解 bug、丢弃冗余 tool 输出 + 保留最近 5 个文件）、结构化笔记（外部 NOTES.md/todo，跨 reset 恢复）、子 agent 隔离（子 agent 吃掉数万 token，只回传 1000–2000 token 摘要）
- quote: "Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary... the five most recently accessed files... Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: primary
- published: 2025-09-29
- confidence: high

### [14] Anthropic 平台侧 token 预算工具：context editing 自动清陈旧 tool call/result + 文件型 memory tool；内部 agentic search 评测上 memory+editing 合计 +39%、editing 单独 +29%；100 轮 web search 评测 token 消耗降 84%
- quote: "context editing automatically clears stale tool calls and results from within the context window when approaching token limits... combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement. In a 100-turn web search evaluation... reducing token consumption by 84%."
- url: https://www.anthropic.com/news/context-management
- source_type: primary
- published: 2025-09-29
- confidence: high

### [15] vLLM 自动前缀缓存为块级哈希：块哈希 = hash(父块哈希, 本块 token, 额外哈希如 LoRA/多模态/cache_salt)；只缓存满块；命中块按 LRU 被 touch 保护；未命中的部分块不缓存
- quote: "We only cache full blocks... we hash each kv-cache block by the tokens in the block and the tokens in the prefix before the block... Parent hash value... Block tokens... Extra hashes... If the head block is a cached block, this also 'evicts' the block"
- url: https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html
- source_type: primary
- published: 2026-06-23
- confidence: high
