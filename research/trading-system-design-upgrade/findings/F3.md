# F3: Reliability engineering for LLM structured output in production (schema validation, constrained decoding, retries, fallbacks, guardrails, failure rates)

## Findings

### [1] OpenAI reports that schema training alone reached only 93% adherence on its complex-schema eval, and that the remaining gap had to be closed with deterministic constrained decoding rather than prompting.
- quote: "despite this model's performance improvements (93% on our benchmark), it still did not meet the reliability that developers need to build robust applications. So we also took a deterministic, engineering-based approach to constrain the model's outputs to achieve 100% reliability."
- url: https://openai.com/index/introducing-structured-outputs-in-the-api/
- source_type: primary
- published: 2024-08-06
- confidence: high

### [2] OpenAI's headline "100% reliability" figure is conditional: `gpt-4o-2024-08-06` with `strict: true` scored a perfect 100% on their complex-JSON-schema eval, versus under 40% for `gpt-4-0613` and 93% for the same new model without the decoder constraint.
- quote: "our new model `gpt-4o-2024-08-06` with Structured Outputs scores a perfect 100%. In comparison, `gpt-4-0613` scores less than 40%."
- url: https://openai.com/index/introducing-structured-outputs-in-the-api/
- source_type: primary
- published: 2024-08-06
- confidence: high

### [3] Even with strict structured outputs, the schema guarantee is voided by two ordinary runtime conditions — a refusal or a stop condition — so a production caller must branch on `refusal` and `finish_reason` instead of assuming valid JSON.
- quote: "The model can fail to follow the schema if the generation reaches `max_tokens` or another stop condition before finishing."
- url: https://openai.com/index/introducing-structured-outputs-in-the-api/
- source_type: primary
- published: 2024-08-06
- confidence: high

### [4] Strict structured outputs is explicitly incompatible with parallel tool calls, so systems that batch tool invocations must set `parallel_tool_calls: false` or accept unvalidated output.
- quote: "Structured Outputs is not compatible with parallel function calls. When a parallel function call is generated, it may not match supplied schemas."
- url: https://openai.com/index/introducing-structured-outputs-in-the-api/
- source_type: primary
- published: 2024-08-06
- confidence: high

### [5] Constrained decoding is implemented by compiling each JSON Schema into a context-free grammar and caching the artifact, so the first request with a new schema carries a large one-off latency penalty that later requests avoid.
- quote: "Typical schemas take under 10 seconds to process on the first request, but more complex schemas may take up to a minute."
- url: https://openai.com/index/introducing-structured-outputs-in-the-api/
- source_type: primary
- published: 2024-08-06
- confidence: high

### [6] On 9,558 real-world JSON schemas, OpenAI's API declared support for only 6% of the JsonSchemaStore schemas and 9% of the hard GitHub schemas — versus 100% of the easy GlaiveAI function-call schemas — so a high compliance rate can coexist with near-total rejection of complex schemas.
- quote: "closed-source grammar engines consistently have the lowest coverage; they came in last on all but one dataset"
- url: https://arxiv.org/abs/2501.10868
- source_type: primary
- published: 2025-02-27 (v3; v1 2025-01-18)
- confidence: high

### [7] JSONSchemaBench defines a compliance rate = empirical coverage / declared coverage precisely to separate "accepts the schema" from "actually enforces it", and shows even open-source decoders fall well below 1.0 on hard schemas (Outlines 0.06 on GitHub-Hard, 0.23 on the Washington Post API; Guidance 0.69 on GitHub-Hard).
- quote: "The Compliance Rate estimates the reliability of the constrained decoding framework in guaranteeing compliance given it accepts a given schema."
- url: https://arxiv.org/abs/2501.10868
- source_type: primary
- published: 2025-02-27 (v3; v1 2025-01-18)
- confidence: high

### [8] Constrained decoding is not purely a reliability tax: the same benchmark measured up to a 50% generation speedup, a 2x spread in schema support between best and worst frameworks, and up to 4% improvement on downstream task accuracy.
- quote: "Constrained decoding can speed up the generation process by 50% compared to unconstrained decoding"
- url: https://arxiv.org/abs/2501.10868
- source_type: primary
- published: 2025-02-27 (v3; v1 2025-01-18)
- confidence: high

### [9] Imposing JSON/XML format restrictions measurably degrades reasoning, and the degradation grows with stricter constraints — the core argument for keeping reasoning free-form and confining structure to the final answer.
- quote: "we observe a significant decline in LLMs reasoning abilities under format restrictions. Furthermore, we find that stricter format constraints generally lead to greater performance degradation in reasoning tasks."
- url: https://arxiv.org/abs/2408.02442
- source_type: primary
- published: 2024-10-14 (v3; v1 2024-08-05)
- confidence: high

### [10] A 2026 study on an 8B model found that forcing structured reflection via Outlines constrained decoding produced an "alignment tax" — near-perfect syntactic conformance while semantic errors went undetected ("structure snowballing"), i.e. schema validity is not a proxy for output correctness.
- quote: "the agent achieves near-perfect superficial syntactic alignment yet fails to detect or resolve deeper semantic errors"
- url: https://arxiv.org/abs/2604.06066
- source_type: primary
- published: 2026-04-07
- confidence: medium

### [11] Decoupling planning from formatting — generate an unconstrained draft, then apply constrained decoding conditioned on that draft — raised strict structured accuracy by up to +24 percentage points over standard constrained decoding (GSM8K 15.2% to 39.0% with a 1B model) with no training.
- quote: "DCCD improves strict structured accuracy by up to +24 percentage points over standard constrained decoding (e.g., 15.2\% to 39.0\% on GSM8K with a 1B model)"
- url: http://export.arxiv.org/api/query?search_query=abs:%22constrained+decoding%22+AND+abs:%22structured%22&start=0&max_results=30
- source_type: primary
- published: 2026-02-08 (arXiv 2603.03305)
- confidence: medium

### [12] A single-call hybrid (free-form reasoning until a trigger token, structured decoding only after it) is reported to "virtually eradicate" premature triggering and gain up to 27% accuracy over natural generation — a portable middle ground between JSON mode and full constrained decoding.
- quote: "The model first performs unconstrained reasoning and only applies structured decoding after a trigger token is generated, explicitly decoupling reasoning from formatting."
- url: http://export.arxiv.org/api/query?search_query=abs:%22constrained+decoding%22+AND+abs:%22structured%22&start=0&max_results=30
- source_type: primary
- published: 2026-01-12 (arXiv 2601.07525, v2 2026-05-28)
- confidence: medium

### [13] Instructor's production guidance separates SDK transport retries from validation retries (same-named `max_retries` in two places) and gives concrete per-error-class attempt budgets: validation errors 2-3 attempts with 1s min / 10s max delay, rate limits 5 attempts with 1s min / 60-120s max, network errors 4 attempts with 2s min / 30s max.
- quote: "Validation errors 2-3 1s 10s"
- url: https://python.useinstructor.com/concepts/retrying/
- source_type: primary
- published: unknown
- confidence: high

### [14] Instructor's default reliability pattern is validate-with-Pydantic then re-ask the model with the validation error text injected, plus a `token_budget` stop condition that aborts retries once cumulative provider usage crosses a positive token limit.
- quote: "Use `token_budget` to stop validation retries after cumulative provider usage reaches a positive token limit"
- url: https://python.useinstructor.com/concepts/retrying/
- source_type: primary
- published: unknown
- confidence: high

### [15] Closed-loop runtime control at decode time (monitor drift from the output contract, then bias/mask/rollback) improved first-attempt success by 20-37.8 percentage points with up to 88% latency reduction in failure-dominated settings, and the author argues many failures are decoding artifacts rather than task misunderstanding.
- quote: "improves first-attempt success rates by 20 to 37.8 percentage points, with up to 88% latency reduction in failure-dominated settings"
- url: https://arxiv.org/abs/2603.27905
- source_type: primary
- published: 2026-04-06 (v2; v1 2026-03-29)
- confidence: medium

### [16] An alternative to relying on the generator is a model-agnostic post-processing layer: a fine-tuned Mistral-7B transformer plus constrained decoding reached 99.5% schema accuracy and 94.0% content similarity, beating Claude-3.5-Sonnet by +25 and +20 percentage points respectively.
- quote: "fine-tuned Mistral-7B model with constrained decoding achieves near perfect schema accuracy (99.5%) and content similarity (94.0%), outperforming Claude-3.5-Sonnet by substantial margins (+25 and +20 percentage points, respectively)"
- url: http://export.arxiv.org/api/query?search_query=abs:%22constrained+decoding%22+AND+abs:%22structured%22&start=0&max_results=30
- source_type: primary
- published: 2025-05-06 (arXiv 2505.04016)
- confidence: medium

### [17] A practitioner building LLM pipeline tooling reports that failures persist even with JSON mode / structured outputs — shape drift, empty required fields, timeouts and rate limits — with downstream automations failing silently, and mitigates it by validating against a schema, retrying with error context, falling back to another model, and logging every request for replay.
- quote: "Even with JSON mode or structured outputs, this still happens occasionally."
- url: https://hn.algolia.com/api/v1/search?query=structured+outputs+JSON+schema+reliability&tags=story&hitsPerPage=20
- source_type: community
- published: 2026-03-08
- confidence: medium

### [18] A practitioner using `gpt-5-mini` in structured-output text mode with a discriminated-union action schema reported semantic selection failures — the schema was satisfied exactly while the model emitted the wrong action — and found that adding ad-hoc system-prompt rules did not fix it.
- quote: "I'm running into action selection reliability issues. Sometimes the model chooses the wrong action entirely, for example emitting a move action when the transcript clearly implies creation."
- url: https://hn.algolia.com/api/v1/search?query=structured+outputs+JSON+schema+reliability&tags=story&hitsPerPage=20
- source_type: community
- published: 2025-12-16
- confidence: medium

## Dead ends
- DuckDuckGo (`duckduckgo.com/html`, `lite.duckduckgo.com/lite`) returned transport errors on every attempt; `search.marcia.cc` likewise unreachable.
- Bing (`bing.com/search`) returned region-locked Chinese-language results regardless of `setmkt=en-US&setlang=en&cc=US`; unusable for English technical queries.
- Mojeek returned HTTP 403.
- `docs.claude.com` and `docs.anthropic.com` tool-use pages returned transport errors, so no Anthropic primary-source claims were captured.
- `gorilla.cs.berkeley.edu/leaderboard.html` (Berkeley Function Calling Leaderboard) unreachable, so no BFCL tool-calling accuracy numbers.
- HN Algolia search for "structured outputs JSON schema reliability" returned only 3 hits, all Show/Ask HN posts — no substantial practitioner post-mortem with hard failure percentages was found via this route.
- No source found that publishes a clean production failure-rate percentage for a specific real system; the strongest quantitative evidence is benchmark-based (JSONSchemaBench) rather than field telemetry.

## Suggested follow-ups
- Which JSON Schema keywords (recursive `$ref`, `anyOf`/discriminated unions, string `format`, `pattern`) are the ones that collapse declared coverage, so a small system can hand-write schemas that stay inside the supported subset?
- What is the measured cost/benefit of a cheap non-LLM post-validator + single re-ask (deterministic repair, e.g. clamping/renaming fields) versus a second full LLM call, for trade-decision JSON specifically?
- Do provider-side grammar caches and first-request schema-compilation latency create a cold-start hazard for a system that generates per-request dynamic schemas (e.g. schemas parameterised by current positions)?
