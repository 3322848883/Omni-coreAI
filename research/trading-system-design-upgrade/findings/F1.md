# F1: Architecture of multi-agent LLM trading frameworks (role decomposition, communication topology, memory layers, decision→order path)

## Findings

### [1] TradingAgents decomposes the system into exactly seven LLM agent roles across four teams, forming a fixed sequential pipeline from analysis to execution.
- quote: "TradingAgents defines seven distinct agent roles within a simulated trading firm: Fundamentals Analyst, Sentiment Analyst, News Analyst, Technical Analyst, Researcher, Trader, and Risk Manager."
- url: https://arxiv.org/html/2412.20138v7
- source_type: primary
- published: 2025-06-03 (v7; v1 2024-12-28)
- confidence: high

### [2] TradingAgents' core anti-pattern fix is replacing natural-language message history with a structured shared "global state" of documents; natural language is reserved for debate only, and a facilitator agent writes the debate outcome back as a structured entry.
- quote: "In contrast to previous multi-agent trading frameworks, which rely heavily on natural language dialogue, TradingAgents agents communicate primarily through structured documents and diagrams."
- url: https://arxiv.org/html/2412.20138v7
- source_type: primary
- published: 2025-06-03
- confidence: high

### [3] TradingAgents tiers models by task depth rather than using one model everywhere: cheap/fast models do retrieval and summarisation, expensive reasoning models do analysis and decisions, and the split is what makes the system runnable without a GPU.
- quote: "all analyst nodes rely on deep-thinking models to ensure robust analysis, while quick-thinking models handle data retrieval from APIs and tools for efficiency. ... This implementation strategy ensures that TradingAgents can be deployed without requiring a GPU, relying only on API credits."
- url: https://arxiv.org/html/2412.20138v7
- source_type: primary
- published: 2025-06-03
- confidence: high

### [4] The reference implementation is a LangGraph graph, and by v0.4.0 the three decision-adjacent nodes (Research Manager, Trader, Portfolio Manager) were converted to structured-output agents.
- quote: "We built TradingAgents with LangGraph to ensure flexibility and modularity. ... \[2026-04\] **TradingAgents v0.2.4** released with structured-output agents (Research Manager, Trader, Portfolio Manager), LangGraph checkpoint resume, persistent decision log"
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10 (README as fetched; release note 2026-04)
- confidence: high

### [5] Crash recovery is implemented as opt-in LangGraph per-node checkpointing into one SQLite file per ticker, cleared on successful completion — a directly portable durability pattern for a single-developer system.
- quote: "Checkpoint resume is opt-in via `--checkpoint`. When enabled, LangGraph saves state after each node so a crashed or interrupted run resumes from the last successful step instead of starting over. ... Per-ticker SQLite databases live at `~/.tradingagents/cache/checkpoints/<TICKER>.db`"
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10
- confidence: high

### [6] TradingAgents' memory layer is a plain append-only markdown decision log that self-settles: once a holding period elapses, the system fetches realised return plus alpha versus the instrument's regional benchmark and writes a one-paragraph reflection that the Portfolio Manager later reads.
- quote: "While the analysts of a later run work, TradingAgents settles every logged decision whose holding period has passed: it fetches the realised return (raw, and alpha against the instrument's regional benchmark) and generates a one-paragraph reflection. The Portfolio Manager then reads the most recent decisions for the same ticker plus recent lessons from other tickers"
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10
- confidence: high

### [7] TradingAgents treats point-in-time data integrity as an architectural constraint, not a data-vendor detail: past-dated runs get SEC EDGAR figures exactly as filed and are explicitly told when a vendor (Yahoo) cannot certify what was public at that date.
- quote: "A run dated in the past reads the statements exactly as they stood that day: a fiscal year that has ended but has not been filed yet is not served, and a figure restated later still reads as first reported. ... Other companies' statements come from Yahoo Finance, which dates a statement by the period it covers rather than by when it was published. A run dated today reads them; a run dated in the past is told they are withheld"
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10
- confidence: high

### [8] The order path in TradingAgents ends in an explicit human-role gate: the risk team advises, and a Portfolio Manager node approves or rejects, with execution handed to a simulated exchange — the LLM never touches the exchange API directly.
- quote: "The risk management team evaluates and adjusts trading strategies, providing assessment reports to the Portfolio Manager for final decision. The Portfolio Manager approves/rejects the transaction proposal. If approved, the order will be sent to the simulated exchange and executed."
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10
- confidence: high

### [9] FinCon uses a manager-analyst hierarchy where seven analyst agent types each own exactly one input modality/source, and a single manager agent is the sole decision-maker — the stated purpose is cutting peer-to-peer communication cost.
- quote: "We implement seven distinct types of analyst agents using LLMs, each producing unique investment insights ... each agent processes information from a single source in a uni-modal fashion ... the manager agent acts as the sole decision-maker, responsible for generating trading actions for sequential financial tasks."
- url: https://arxiv.org/html/2407.06567v3
- source_type: primary
- published: 2024-11-07 (v3; v1 2024-07-09)
- confidence: high

### [10] FinCon's risk control is dual-level: an intraday CVaR trigger that forces a risk-averse stance, plus an inter-episode "conceptual verbal reinforcement" loop that rewrites agent prompts using the overlap percentage of consecutive trading decision sequences as a textual learning rate, propagating beliefs only to the agents that need them.
- quote: "Conditional Value at Risk (CVaR) represents the average of the worst-performing 1% of daily trading Profits and Losses (PnLs). ... we derive investment belief updates by measuring the overlapping percentage of trading actions between two consecutive training trajectories at each belief update ... These belief updates are first received by the manager agent and then selectively propagated to relevant agents, minimizing over-communication."
- url: https://arxiv.org/html/2407.06567v3
- source_type: primary
- published: 2024-11-07
- confidence: high

### [11] FinCon cleanly separates LLM judgement from position sizing: the LLM emits only a directional buy/sell/hold per asset, and an external mean-variance convex optimisation solver converts those directions into portfolio weights, rebalanced daily.
- quote: "the manager agent determines the portfolio weights for all stocks using an external optimization solver that applies the mean-variance optimization ... where w is portfolio weights vector, μ and Σ are the shrinkage estimators of N-dimensional sample expected return and N×N sample covariance matrix"
- url: https://arxiv.org/html/2407.06567v3
- source_type: primary
- published: 2024-11-07
- confidence: high

### [12] FinMem's architecture is three modules — Profiling (persona), layered Memory (hierarchical message processing with an adjustable "cognitive span"), and Decision-making (memory→decision) — i.e. persona and memory are configuration, not prompt text.
- quote: "It encompasses three core modules: Profiling, to customize the agent's characteristics; Memory, with layered message processing, to aid the agent in assimilating hierarchical financial data; and Decision-making, to convert insights gained from memories into investment decisions."
- url: https://arxiv.org/abs/2311.13743
- source_type: primary
- published: 2023-12-03 (v2; v1 2023-11-23)
- confidence: high

### [13] A 2026 crypto-specific MAS paper benchmarks three communication topologies head-to-head and finds hierarchy wins on risk-adjusted return while debate wins raw bull-market return but amplifies losses — architecture choice is a regime-dependent trade-off, not a solved question.
- quote: "the hierarchical design provides the best risk-adjusted return in the full period (Hierarchical (Skill) SR =+1.502) and the strongest capital preservation in the bear market (Hierarchical (CoT) MDD =−4.42%) ... the debate architecture achieves the highest raw returns in bull conditions (Debate (Skill) +290.96%) but is prone to amplified losses in adverse markets"
- url: https://arxiv.org/html/2501.00826v3
- source_type: primary
- published: 2026-06-16 (v3; v1 2025-01-01)
- confidence: high

### [14] That same crypto MAS is built as three modality-specialised agents (Crypto / News / Trading) with the Trading Agent fusing signals plus live portfolio state — and its ablation shows the market-data agent carries nearly all the directional alpha while news is mainly a risk damper.
- quote: "the Crypto Agent is the most critical component: its removal produces the largest degradation across all four metrics, reducing cumulative return by 42.57 percentage points ... memory provides meaningful continuity: removing the rolling memory window costs 11.47 percentage points in cumulative return"
- url: https://arxiv.org/html/2501.00826v3
- source_type: primary
- published: 2026-06-16
- confidence: high

### [15] The crypto MAS memory layer is deliberately small and serialisable — a rolling window of the last 4 weekly outputs prepended to the prompt, persisted between weeks for run resumption, and updated only with the final output of multi-round debates so intermediate reasoning never contaminates the longitudinal record.
- quote: "All agents maintain a rolling memory of their K=4 most recent weekly outputs. Before each new call, the memory block is prepended to the user message in reverse chronological order ... When operating in refinement or debate rounds within the collaborative and debate architectures, the agent's memory is updated only with the final-round output so that intermediate reasoning steps do not pollute the longitudinal record."
- url: https://arxiv.org/html/2501.00826v3
- source_type: primary
- published: 2026-06-16
- confidence: high

### [16] The decision→order conversion in the crypto MAS is a deterministic engine behind a strict JSON contract: the LLM outputs a fractional action per asset in [-1,1] and the engine sequences sells before buys, scales buys down proportionally if over-allocated, and charges 0.1% per side.
- quote: "All sell orders execute first; the resulting cash is then redistributed simultaneously across all assets with positive actions, with fractions scaled down proportionally if their sum exceeds unity. ... A transaction cost of 0.1% per trade side is applied to all executed orders"
- url: https://arxiv.org/html/2501.00826v3
- source_type: primary
- published: 2026-06-16
- confidence: high

### [17] TiMi (Microsoft Research Asia + Tongji) is the strongest example of architected analysis/execution separation: agents develop and tune a programmatic trading bot offline, and the live path is pure code with no LLM inference, making the efficiency gain scale with trade frequency.
- quote: "TiMi implements a decoupling mechanism where the initial two stages develop and optimize prototype trading bots through offline simulations by leveraging specialized LLM capabilities, while the deployment stage executes thoroughly refined bots with tuned parameters in live trading. ... This mechanism eliminates the requirement for continuous model inference during actual deployment"
- url: https://arxiv.org/html/2510.04787v2
- source_type: primary
- published: 2026-02-09 (v2; v1 2025-10-06)
- confidence: high

### [18] TiMi's four agents are split by capability, not persona — macro analysis (semantic), strategy adaptation (semantic + math), bot evolution (code LLM), feedback reflection (math) — and its bot is layered into strategy/function/parameter tiers governed by three explicit programming laws, with refinement escalating parameter→function→strategy only when lower levels fail.
- quote: "We propose a hierarchical optimization scheme that propagates refinements from the parameter level ... upward through the trading system. At the parameter level, we focus on fine-tuning numerical values within constraints. When parameter adjustments prove insufficient to meet requirements (e.g., failing risk simulations), Afr escalates to function level and substitutes algorithmic components. The highest level of intervention occurs at the strategy layer"
- url: https://arxiv.org/html/2510.04787v2
- source_type: primary
- published: 2026-02-09
- confidence: high

### [19] TiMi's live execution layer is plain engineering with no LLM in the loop: LIMIT-only entries, dynamically placed/cancelled TAKE_PROFIT and STOP orders, MARKET orders reserved for risk liquidation, pre-trade price-deviation checks, funding-rate-aware position reduction, and stateless recovery that re-reads state from the exchange.
- quote: "(1) LIMIT orders serve as the exclusive mechanism for opening positions based on volatility-derived formulas; (2) TAKE_PROFIT and STOP orders are dynamically placed and cancelled during position monitoring; and (3) MARKET orders are utilized for risk management purposes ... At the system level, state information is fetched directly from the exchange, enabling a stateless execution logic. This allows the bots to recover at any time without losing trading context."
- url: https://arxiv.org/html/2510.04787v2
- source_type: primary
- published: 2026-02-09
- confidence: high

### [20] TiMi's measured latency budget confirms the execution layer is I/O-bound, not inference-bound: end-to-end 137 ms average / 185 ms P99, of which market retrieval is 85 ms and internal logic only 5 ms.
- quote: "(1) Market Retrieval 85 12 115 (2) Internal Logic 5 <1 5 (3) Trade Request 47 8 65 Total End-to-End 137 15 185"
- url: https://arxiv.org/html/2510.04787v2
- source_type: primary
- published: 2026-02-09
- confidence: medium

### [21] TiMi deliberately excludes news/social data and emotional persona framing, using only objective technical indicators (volume, amplitude) over dynamically updated windows — an explicit counter-position to the analyst-persona school.
- quote: "the simulation of human trading organizations (e.g., sentiment/news analysts, traders with varying risk preferences) in previous research inadvertently introduces interference from emotional biases and subjective judgments simulated by agents ... we utilize objective technical indicators of target pairs (e.g., volume and amplitude) with dynamically updated time windows"
- url: https://arxiv.org/html/2510.04787v2
- source_type: primary
- published: 2026-02-09
- confidence: high

### [22] A 2025 Bitcoin-specific multi-agent system replaces gradient updates with a verbal feedback loop: a dedicated Reflect agent issues daily and weekly natural-language critiques of decisions, which are injected into future prompts so agents adjust allocation logic with no fine-tuning.
- quote: "The agents improve over time via a novel verbal feedback mechanism where a Reflect agent provides daily and weekly natural-language critiques of trading decisions. These textual evaluations are then injected into future prompts of the agents, allowing them to adjust allocation logic without weight updates or finetuning."
- url: http://export.arxiv.org/api/query?search_query=all:%22cryptocurrency%22+AND+all:%22multi-agent%22+AND+all:%22LLM%22 (abstract of arXiv:2510.08068, "An Adaptive Multi Agent Bitcoin Trading System")
- source_type: primary
- published: 2025-10-09 (v2 2025-11-14)
- confidence: medium

### [23] The live-vs-backtest gap is acknowledged explicitly in the most mature open-source system: TradingAgents ships a backtest grid that scores each cell on realised alpha against a regional benchmark, but states returns are not reproducible and frames itself as a research scaffold rather than a strategy.
- quote: "Backtest results are not guaranteed to match any published figure. Returns depend on the model, the temperature, the date range, data quality, and the sampling above. Treat the framework as a research scaffold for studying multi-agent analysis, not as a strategy with a fixed, replicable return."
- url: https://github.com/TauricResearch/TradingAgents
- source_type: primary
- published: 2026-10
- confidence: high

## Suggested follow-ups
- How do these frameworks handle the LLM→exchange boundary operationally (idempotent order IDs, reconciliation against exchange state, duplicate-order prevention) once real capital is involved? TiMi's appendix and TradingAgents' issues/discussions are the likely primary sources.
- What does a minimal viable memory layer look like for a small account — is TradingAgents' append-only markdown log with settled reflections sufficient, or does the layered/decay memory of FinMem/TradingGPT earn its complexity? TradingGPT (arXiv:2309.03736) is the unread primary source for layered memory.
- Does the "agents write code, deployment runs code" pattern (TiMi) transfer to a Python monolith on Gate.io perps, and what is the minimum viable version — e.g. LLM emits a parameterised strategy config rather than generated code?
