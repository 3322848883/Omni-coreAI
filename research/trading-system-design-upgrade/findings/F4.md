# F4: Order/position state consistency between a trading bot and the exchange (idempotent submission, reconciliation, orphan protective orders, partial fills, exactly-once vs at-least-once)

## Findings

### [1] A production-grade open-source trading platform (NautilusTrader) states plainly that it does NOT guarantee exactly-once delivery for submit/modify/cancel, and encodes a three-part "safety test" that decides whether a transient failure may be retried at all.
- quote: "NautilusTrader does not guarantee exactly-once delivery for submit, modify, or cancel commands. ... An adapter retries a transient failure only when a repeat is safe. A repeat is safe when it cannot apply a state change twice, cannot change an order the first attempt did not name, and cannot report an earlier success as a rejection."
- url: https://nautilustrader.io/docs/latest/concepts/execution/policies/
- source_type: primary
- published: unknown (docs for current `latest` release)
- confidence: high

### [2] The same docs document that the retry gate is NOT fully honoured across real venues: some order commands can be sent twice on transient failure on named exchanges.
- quote: "A transient failure can send some order commands twice, including on Bybit, OKX, and Kraken spot. That list is not a complete census."
- url: https://nautilustrader.io/docs/latest/concepts/execution/policies/
- source_type: primary
- published: unknown
- confidence: high

### [3] Idempotency in practice is approximated with venue trade/fill identity, not with an application-level event id: an order rejects a second fill carrying the same `trade_id`, and reconciliation-generated fills use deterministic IDs so a restart replay deduplicates to the same key.
- quote: "NautilusTrader does not use `event_id` as a universal order-level deduplication key and does not guarantee exactly-once application for every order event. Its narrower protections are: An order rejects a second fill with the same `trade_id`. The execution engine prevents the same `trade_id` from being applied again to the target position." / "Synthetic and inferred reconciliation fills use deterministic IDs. Replaying the same inputs after a restart therefore produces the same `trade_id` and is deduplicated."
- url: https://nautilustrader.io/docs/latest/concepts/execution/policies/ and https://nautilustrader.io/docs/latest/concepts/execution/
- source_type: primary
- published: unknown
- confidence: high

### [4] The write-ahead/persistence boundary is explicitly not atomic with the wire send: the order and its client order ID are enqueued to the cache before the client call, but the built-in Redis/PostgreSQL backends write asynchronously, so a crash can leave an order live at the venue that the bot never durably recorded.
- quote: "The enqueue steps fail before the client call when the cache backend cannot accept them. Successful enqueue does not mean the backing store has committed the order or origin. The built-in Redis and PostgreSQL cache backends process these writes asynchronously." / "A process failure can therefore occur after the venue receives an order but before the local order and origin become durable. Startup reconciliation can recover that order when the venue reports it, but incomplete venue history can leave the node without enough evidence to reconstruct the full execution history."
- url: https://nautilustrader.io/docs/latest/concepts/execution/policies/
- source_type: primary
- published: unknown
- confidence: high

### [5] Reconciliation is fail-closed on positions: an explicit position report (including an explicit flat report) is authoritative and the node refuses to start if it cannot be aligned within tolerance; absence of a report must never be read as "flat".
- quote: "An explicit position report is authoritative. During startup reconciliation, the engine either aligns to that report within reconciliation tolerances or fails closed. ... Not evidence of a flat position: A missing report. A null quantity. A venue that does not publish positions." / "Unresolved reports prevent actors and strategies from starting."
- url: https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/
- source_type: primary
- published: unknown
- confidence: high

### [6] Runtime order-state drift is resolved by a documented decision table plus three concrete anti-false-positive mechanisms: a recent-activity grace window, a targeted single-order query before any terminal "not found" resolution, and query throttling.
- quote: "The engine skips reconciliation for orders whose last event falls within the `open_check_threshold_ms` window. This prevents false positives from race conditions where the venue is still processing." / "Before applying a terminal \"not found\" resolution, the engine issues a single-order query to the venue. This catches false negatives from bulk query limitations or timing delays." / "The engine caps single-order queries per cycle via `max_single_order_queries_per_cycle`. Remaining orders are deferred to the next cycle. `single_order_query_delay_ms` spaces out consecutive queries to avoid rate limits."
- url: https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/
- source_type: primary
- published: unknown
- confidence: high

### [7] Ambiguous in-flight commands are deliberately left unresolved rather than force-resolved, and locally-forced terminal states are explicitly distinguished from venue-confirmed ones.
- quote: "`PENDING_UPDATE` / *Not found* → *Unresolved*: Modification outcome remains unknown." / "Local terminal state is not venue confirmation. The first row is backed by an explicit venue status. The remaining rows restore a terminal local state after an operator-configured retry policy expires. They do not prove that the venue rejected the submit or canceled the working order."
- url: https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/ and https://nautilustrader.io/docs/latest/concepts/execution/policies/
- source_type: primary
- published: unknown
- confidence: high

### [8] Orphan/stale order cleanup has two independent layers in that design: an unacknowledged submission can be retained as unresolved instead of being synthetically rejected (`submission_recovery_policy`), and a "broad" cancel-all is routed to the venue even when the bot has no matching local order, which is the documented way to remove venue-side orders missing from the local cache.
- quote: "The command therefore reaches the resolved execution client even when NautilusTrader has no matching local order. This allows a venue bulk-cancel endpoint to remove an order that exists at the venue but is missing from the local cache." / "`submission_recovery_policy` defaults to `ResolveLocally`. Selecting `RetainUnresolved` enables submission identity tracking, exhaustion diagnostics, and preservation of the submission's recovery budget until acknowledgement."
- url: https://nautilustrader.io/docs/latest/concepts/execution/ and https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/
- source_type: primary
- published: unknown
- confidence: high

### [9] Protective exits whose size must match the live position are handled as a distinct, allowlisted venue capability: a stop with `close_position=true` + `reduce_only=true` carries only a placeholder quantity, is treated as position-reducing, and skips min/max quantity and notional checks — but only for venues whose adapter enforces whole-position closing.
- quote: "Some execution clients support conditional exits whose venue determines the closing quantity from the open position when the trigger fires. Nautilus orders still carry a placeholder quantity for local validation. The `full_position_exit_venues` setting ... identifies venues whose execution clients enforce these semantics. It defaults to empty." / "Only allowlist a venue when its downstream execution client enforces whole-position closing."
- url: https://nautilustrader.io/docs/latest/concepts/execution/
- source_type: primary
- published: unknown
- confidence: high

### [10] Gate.io (the exchange in scope) auto-cancels protective/reduce-only orders when the position they reference disappears, i.e. the venue itself removes most orphan protective orders — `finish_as` values include `position_closed`, `reduce_only` and `reduce_out`.
- quote: "**finish_as** ... How the order was finished: - filled: all filled - cancelled: manually cancelled - liquidated: cancelled because of liquidation - ioc: time in force is `IOC`, finish immediately - auto_deleveraged: finished by ADL - reduce_only: cancelled because of increasing position while `reduce-only` set - position_closed: cancelled because the position was closed - reduce_out: only reduce positions by excluding hard-to-fill orders - stp: cancelled because self trade prevention"
- url: https://github.com/gateio/gateapi-python/blob/master/docs/FuturesOrder.md
- source_type: primary
- published: unknown (repo archived by owner on Jul 16, 2026; docs generated from Gate API v4 spec)
- confidence: high

### [11] Gate.io futures orders support a venue-computed close: `close=true` with `size=0`, or in dual (hedge) mode `auto_size=close_long|close_short` with `size=0`, so a protective order does not have to be resized as the position changes — and `text` is the client-order-ID field, constrained to a `t-` prefix, ≤28 bytes, charset `0-9A-Za-z_-.`, with reserved tokens used by the venue for order-source attribution.
- quote: "**close** | **bool** | Set as `true` to close the position, with `size` set to 0" / "**auto_size** | **str** | Set side to close dual-mode position. `close_long` closes the long side; while `close_short` the short one. Note `size` also needs to be set to 0" / "**text** | **str** | Custom order information. If not empty, must follow the rules below: 1. Prefixed with `t-` 2. No longer than 28 bytes without `t-` prefix 3. Can only include 0-9, A-Z, a-z, underscore(_), hyphen(-) or dot(.)"
- url: https://github.com/gateio/gateapi-python/blob/master/docs/FuturesOrder.md
- source_type: primary
- published: unknown (archived Jul 16, 2026)
- confidence: high

### [12] Hyperliquid exposes the three primitives this angle needs: a 128-bit hex client order id (`cloid`) usable for cancellation without the venue order id, position-level TP/SL grouping, and a venue-side dead-man's switch that cancels all open orders on a timer.
- quote: "Client Order ID (cloid) is an optional 128 bit hex string, e.g. `0x1234567890abcdef1234567890abcdef`" / "\"grouping\": \"na\" | \"normalTpsl\" | \"positionTpsl\"" / "Schedule a cancel-all operation at a future time. Not including time will remove the scheduled cancel operation. The time must be at least 5 seconds after the current time. Once the time comes, all open orders will be canceled and a trigger count will be incremented. The max number of triggers per day is 10. This trigger count is reset at 00:00 UTC."
- url: https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint
- source_type: primary
- published: unknown
- confidence: high

### [13] The canonical client-order-ID definition (FIX `ClOrdID`) only requires uniqueness within one trading day and advises date-embedding for multi-day/global firms — so an idempotency key should be constructed to be unique across days, not merely per session.
- quote: "Unique identifier for Order as assigned by the buy-side (institution, broker, intermediary etc.) ... Uniqueness must be guaranteed within a single trading day. Firms, particularly those which electronically submit multi-day orders, trade globally or throughout market close periods, should ensure uniqueness across days, for example by embedding a date within the ClOrdID <11> field."
- url: https://www.onixs.biz/fix-dictionary/4.4/tagnum_11.html
- source_type: primary
- published: unknown (FIX 4.4 dictionary)
- confidence: high

### [14] Partial fills and restart resends are handled with two separate guards: stable `trade_id` dedup across the websocket and polling channels, and a "replayed fills" rule that suppresses position updates for fill reports older than a reconciliation-opened position — with the residual gaps documented rather than hidden.
- quote: "Live fills can arrive through two channels: Real-time fill events arriving via WebSocket. Periodic reconciliation polling the venue for fill history and position status. Stable `trade_id` values let the engine deduplicate the same fill across both channels." / "While a position that reconciliation opened from a venue position report stays open, a fill report for that instrument and account with an earlier `ts_event` updates its order but no position. ... this stops a venue that resends them after a restart, such as Interactive Brokers TWS, from doubling the position."
- url: https://nautilustrader.io/docs/latest/concepts/execution/ and https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/
- source_type: primary
- published: unknown
- confidence: high

### [15] Overfill (cumulative filled > order quantity) is treated as an integrity signal, not silently absorbed: the default rejects the fill and preserves order state, and tolerating it is explicitly not a substitute for duplicate-fill detection.
- quote: "`allow_overfills` ... `False`: Logs and rejects the fill, preserving the order's current state. `True`: Logs a warning, applies the fill, and tracks the excess in `overfill_qty`." / "Choose this setting from the venue's execution contract. The default `False` protects local state but can leave a discrepancy after a legitimate venue overfill. `True` applies the excess quantity and is not a substitute for duplicate-fill detection."
- url: https://nautilustrader.io/docs/latest/concepts/execution/
- source_type: primary
- published: unknown
- confidence: high

## Dead ends
- All general web search engines were unusable from this machine: DuckDuckGo (`duckduckgo.com/html`, `lite.duckduckgo.com`, `html.duckduckgo.com`) and Brave returned transport errors; Mojeek returned 403; Bing (even with `setmkt=en-US`) returned Chinese SEO/spam domains; Ecosia redirected to the Bing home page; Marginalia required an interactive session token. No search-engine result pages yielded usable links.
- Direct hosts that failed with transport/DNS errors (could not be fetched at all): `developers.binance.com` (all Binance futures/derivatives API doc pages, including the `binance-docs.github.io/apidocs/futures/en/` mirror, which 301-redirects there), `www.gate.io/docs/...` (Gate's own API v4 doc site), `bybit-exchange.github.io/docs/v5/order/create-order`, `docs.cdp.coinbase.com`, `raw.githubusercontent.com` (all paths), `docs.kraken.com` ("SSRF protection: DNS resolution failed"). So Binance/Bybit/Kraken/Coinbase primary API docs could NOT be read; the exchange-side claims in this file come from Gate's official SDK docs (mirrored on github.com) and Hyperliquid's official docs.
- `https://docs.deribit.com/articles/order-management.md` → 404; `https://docs.deribit.com/api-reference/trading/private-buy.md` and `https://docs.deribit.com/fix-api/production/overview[.md]` → transport errors, so Deribit's `label`/FIX drop-copy documentation was not obtained.
- `https://api.github.com/repos/gateio/gateapi-python/contents/docs` was fetched but is a full directory listing (200KB+, truncated) — expensive and only useful for locating `docs/FuturesOrder.md`.
