# F2: Engineering practices of mature open-source trading bots (Freqtrade, Hummingbot, Jesse, OctoBot) — order/position modeling, stop-loss enforcement, exchange disconnect & state drift, config/risk layers, backtest-live parity, testing

## Findings

### [1] Freqtrade models a position as a `Trade` row persisted to a database, with a child list of `Order` rows — the DB, not in-memory state, is the source of truth for what the bot holds.
- quote: "A position freqtrade enters is stored in a `Trade` object - which is persisted to the database. It's a core concept of freqtrade - and something you'll come across in many sections of the documentation"
- url: https://www.freqtrade.io/en/stable/trade-object/
- source_type: primary
- published: unknown (docs track `develop` branch)
- confidence: high

### [2] The `Trade` model carries a separate, explicit `Order` child object with a normalised field set (`ft_is_open`, `ft_order_side` including the synthetic value `'stoploss'`, `ft_cancel_reason`, `safe_filled`, `safe_remaining`, `safe_cost`, `stop_price`, `order_filled_utc`), and the docs recommend the `safe_*` accessors because raw exchange fields may be `None`.
- quote: "`ft_order_side` string Order side ('buy', 'sell', or 'stoploss')" / "`safe_remaining` float Remaining amount - either taken from the exchange or calculated."
- url: https://www.freqtrade.io/en/stable/trade-object/
- source_type: primary
- published: unknown
- confidence: high

### [3] Stop-loss state is tracked as first-class position attributes, including `stoploss_last_update_utc` (timestamp of the last on-exchange stop update) and `stoploss_or_liquidation`, which returns the *more restrictive* of the stop and the liquidation price — i.e. the bot computes one canonical "price at which I get forcibly flattened".
- quote: "`stoploss_or_liquidation` float Returns the more restrictive of stoploss or liquidation price and corresponds to the price a stoploss would trigger at."
- url: https://www.freqtrade.io/en/stable/trade-object/
- source_type: primary
- published: unknown
- confidence: high

### [4] Freqtrade places the stop-loss as a real order on the exchange immediately after the entry fills, and refreshes it on a timer rather than every loop — default `stoploss_on_exchange_interval` = 60 seconds — with rate-limit avoidance stated as the explicit reason; the same reconciliation logic re-creates a stop that was cancelled manually on the exchange.
- quote: "The bot cannot do these every 5 seconds (at each iteration), otherwise it would get banned by the exchange. So this parameter will tell the bot how often it should update the stoploss order. The default value is 60 (1 minute). This same logic will reapply a stoploss order on the exchange should you cancel it accidentally."
- url: https://www.freqtrade.io/en/stable/stoploss/
- source_type: primary
- published: unknown
- confidence: high

### [5] There is a documented, named fallback when the on-exchange stop cannot be placed (e.g. the stop is too wide for exchange limits): the bot degrades to the `emergency_exit` order type, which defaults to a market order.
- quote: "Using stoploss on exchange with a very wide stoploss (e.g. -1) may fail to place the stoploss order on exchange due to exchange limitations. In that case, the bot will fallback to using the `emergency_exit` order type to place a market order as placing the stoploss order failed."
- url: https://www.freqtrade.io/en/stable/stoploss/
- source_type: primary
- published: unknown
- confidence: high

### [6] Exchange stop-order capability is an explicit matrix that the bot validates at startup and refuses to boot on a mismatch — and Gate.io futures (the exchange in scope for omnialpha) is listed as supporting stop-loss-on-exchange in **limit** mode only, not market.
- quote: "| [Gate.io](../exchanges/#gateio) | futures | isolated | limit |" / "If your exchange only supports one of the two order types, you must configure your `stoploss` value accordingly, otherwise the bot will fail to start."
- url: https://www.freqtrade.io/en/stable/stoploss/
- source_type: primary
- published: unknown
- confidence: high

### [7] Freqtrade recommends stop-market over stop-limit for stops on the stated grounds that a stop exists to exit a crashing market, and a limit stop that does not fill can produce a loss much larger than the configured stop.
- quote: "we recommend using stoploss-market orders whenever possible, as the main point of a stoploss is to get you out of a position when the market is crashing, and in such situations, you'll want to exit the position immediately at the best available price, rather than risking a limit order not getting filled and potentially incurring even greater losses."
- url: https://www.freqtrade.io/en/stable/stoploss/
- source_type: primary
- published: unknown
- confidence: high

### [8] Risk control is a separate, composable plugin layer ("Protections") rather than strategy code: `StoplossGuard`, `MaxDrawdown`, `LowProfitPairs`, `CooldownPeriod`, each parameterised by a lookback window and a lock duration, each independently configurable multiple times at different levels, and each able to lock either one pair or all pairs.
- quote: "Protections will protect your strategy from unexpected events and market conditions by temporarily stop trading for either one pair, or for all pairs." / "Each Protection can be configured multiple times with different parameters, to allow different levels of protection (short-term / long-term)."
- url: https://www.freqtrade.io/en/stable/plugins/
- source_type: primary
- published: unknown
- confidence: high

### [9] The protection layer is required to be time-injectable so it can run in backtest: protection authors must not call wall-clock time directly but use the supplied `date_now` variable, and lock end times must be computed from the last considered trade to avoid re-locking.
- quote: "No protection should use datetime directly, but use the provided `date_now` variable for date calculations. This preserves the ability to backtest protections."
- url: https://www.freqtrade.io/en/stable/developer/
- source_type: primary
- published: unknown
- confidence: high

### [10] Protections are disabled by default in backtesting and must be explicitly enabled, because simulating them is expensive — meaning the default backtest silently omits the production risk layer unless the operator remembers the flag.
- quote: "Protections are supported by backtesting and hyperopt, but must be explicitly enabled by using the `--enable-protections` flag." / "Will slow backtesting down by a considerable amount, but will include configured protections"
- url: https://www.freqtrade.io/en/stable/backtesting/
- source_type: primary
- published: unknown
- confidence: high

### [11] Freqtrade documents its backtest simulation as an enumerated assumptions contract — fills at requested price with **no slippage** within the candle range, stop-loss exits exactly at the stop price (plus `2 * fees`), stop-loss evaluated before ROI within a candle, "low happens before high" for stops, exit-signal favoured over stop-loss, ROI applied before trailing-stop — and states plainly that backtesting never substitutes for dry-run.
- quote: "Taking these assumptions, backtesting tries to mirror real trading as closely as possible. However, backtesting will **never** replace running a strategy in dry-run mode."
- url: https://www.freqtrade.io/en/stable/backtesting/
- source_type: primary
- published: unknown
- confidence: high

### [12] The framework names callback-frequency mismatch as an explicit backtest/live parity hazard: backtest invokes each callback at most once per candle, while live invokes most callbacks roughly every 5 seconds.
- quote: "Backtesting will call each callback at max. once per candle (`--timeframe-detail` modifies this behavior to once per detailed candle). Most callbacks will be called once per iteration in live (usually every ~5s) - which can cause backtesting mismatches."
- url: https://www.freqtrade.io/en/stable/bot-basics/
- source_type: primary
- published: unknown
- confidence: high

### [13] The mitigation for intra-candle bias is a second, finer timeframe (`--timeframe-detail`) that replays only candles where something is happening, with the constraint that it must be strictly smaller than the main timeframe; entries still occur at the main candle's open but freed trade slots are released earlier.
- quote: "freqtrade can use a lower (faster) timeframe to simulate intra-candle movements." / "`--timeframe-detail` must be smaller than the original timeframe, otherwise backtesting will fail to start."
- url: https://www.freqtrade.io/en/stable/backtesting/
- source_type: primary
- published: unknown
- confidence: high

### [14] The live loop is explicitly exchange-authoritative and re-reads state every iteration in a fixed order: fetch open trades from persistence, then "Update trades open order state from exchange", then evaluate exits and entries.
- quote: "By default, the bot loop runs every few seconds (`internals.process_throttle_secs`) and performs the following actions: - Fetch open trades from persistence. ... - Update trades open order state from exchange."
- url: https://www.freqtrade.io/en/stable/bot-basics/
- source_type: primary
- published: unknown
- confidence: high

### [15] The exchange layer is wrapped in a typed exception hierarchy with dedicated retryable/temporary categories rather than generic error handling: `ExchangeError` branches into `TemporaryError`, `DDosProtection`, and `InvalidOrderException` → `RetryableOrderError`, `InsufficientFundsError`.
- quote: "+---+ ExchangeError |       | |       +---+ TemporaryError |       | |       +---+ DDosProtection |       | |       +---+ InvalidOrderException |           | |           +---+ RetryableOrderError |           | |           +---+ InsufficientFundsError"
- url: https://www.freqtrade.io/en/stable/developer/
- source_type: primary
- published: unknown
- confidence: high

### [16] Exchange integrations are gated by an online test suite run against real public endpoints plus a manual private-endpoint checklist whose items include cross-checking the bot's P&L and fees against the exchange itself.
- quote: "Compare result calculation between exchange and bot" / "Ensure fees are applied correctly (check the database against the exchange)"
- url: https://www.freqtrade.io/en/stable/developer/
- source_type: primary
- published: unknown
- confidence: high

### [17] The contribution/CI bar is concrete and low-overhead for a small project: pre-commit hooks installable in one command (`pre-commit install`, covering `ruff`, `mypy`, `pytest`), new code expected to carry basic unit tests, and "All tests must pass for a PR to be merged to `stable` or `develop`" with CI on Linux/macOS/Windows.
- quote: "All tests must pass for a PR to be merged to `stable` or `develop`."
- url: https://www.freqtrade.io/en/stable/developer/
- source_type: primary
- published: unknown
- confidence: high

### [18] Hummingbot's V2 architecture separates long-running decision code from finite execution code: Controllers/Scripts are long-running, while **Executors** own the order lifecycle (placement, refresh, cancellation) and are explicitly "designed to start and finish" with an `active → closed/failed` state machine.
- quote: "Executors automate a discrete trading workflow — placing, managing, and closing orders according to predefined logic. They are designed to **start and finish**: each executor has a lifecycle (active → closed/failed) and handles its own order management internally."
- url: https://hummingbot.org/strategies/v2-strategies/
- source_type: primary
- published: 2026-09-22 (page last-modified)
- confidence: high

### [19] Hummingbot formalises executor bookkeeping with an `ExecutorOrchestrator`: a dictionary of executors keyed by controller ID, driven by explicit action objects (`CreateExecutorAction`, `StopExecutorAction`, `StoreExecutorAction`), where the store action persists executor data for later performance reporting (realised/unrealised P&L, volume, close-type distribution).
- quote: "It maintains a dictionary of executors, where each executor is associated with a controller ID." / "The `StoreExecutorAction` enables the orchestrator to store executor data, facilitating persistence and analysis of executor performance over time."
- url: https://hummingbot.org/strategies/v2-strategies/executors/
- source_type: primary
- published: 2026-09-22
- confidence: high

### [20] Hummingbot drives all components off one clock: connectors and strategies inherit a common `TimeIterator`, and the Clock calls `c_tick()` on each every `tick_size` (default 1.0s, configurable via `conf_client.yml` / `config tick_size`, hard floor 0.1s "due to connector limitations"); each tick reloads order book snapshots, balances and order status.
- quote: "All the major components of Hummingbot, like the connectors and the strategies inherit from the TimeIterator class. The Clock notifies all the components involved in the strategy by calling the method `c_tick()` of the time iterators every `tick_size`."
- url: https://hummingbot.org/client/global-configs/clock-tick/
- source_type: primary
- published: 2026-09-22
- confidence: high

### [21] Hummingbot connectors reconcile orders through a per-connector `_order_tracker` keyed by the **client-generated** order id, rather than trusting a single order-creation response — visible in the official troubleshooting stack trace.
- quote: "order = connector._order_tracker.fetch_order(client_order_id=order_id)"
- url: https://hummingbot.org/troubleshooting/
- source_type: primary
- published: 2026-09-22
- confidence: high

### [22] Hummingbot's WebSocket layer is written to absorb disconnects as a logged, timed retry rather than a crash, and the docs treat reconnection as routine operational noise.
- quote: "ERROR - Unexpected error with Kraken WebSocket connection. Retrying after 30 seconds..."
- url: https://hummingbot.org/troubleshooting/
- source_type: primary
- published: 2026-09-22
- confidence: high

### [23] Freqtrade's backtest report includes a statistical significance gate by default — "Mean profit p-value", a two-sided one-sample Student's t-test against the null that mean per-trade return is zero, with 0.05 as the usual bar — so "is this edge distinguishable from noise" is an output artifact, not a manual judgement.
- quote: "Two-sided p-value of a one-sample Student's t-test against the null hypothesis that the mean per-trade return is zero - in short, 'is the average profit distinguishable from noise?' A small value (the usual bar is below `0.05`) means the observed edge is unlikely to be down to chance."
- url: https://www.freqtrade.io/en/stable/backtesting/
- source_type: primary
- published: unknown
- confidence: high

### [24] Jesse's documented feature set treats statistical robustness as a first-class module rather than a strategy concern — dedicated Monte Carlo analysis (trade-order shuffling, candle-based, candle pipelines) and bootstrap-based "Rule Significance Testing", plus a benchmark tab under Backtest.
- quote: "Monte Carlo Analysis / Trade-Order Shuffling / Candles-Based / Candle Pipelines" and "Rule Significance Testing / How It Works (Bootstrap)"
- url: https://docs.jesse.trade/docs/getting-started/
- source_type: primary
- published: unknown (docs site copyright 2020-2025)
- confidence: medium

### [25] Jesse's live/paper trading is delivered as a licence-gated binary plugin (`jesse install-live` with a `LICENSE_API_TOKEN`), not as open source — so its live-trading engineering is not inspectable, even though the backtest/optimisation core is open.
- quote: "Live and paper trading functionality is supported by Jesse via an official plugin." / "The package is pre-built and the access is limited to those with an active license."
- url: https://docs.jesse.trade/docs/livetrade
- source_type: primary
- published: unknown
- confidence: high

## Dead ends
- DuckDuckGo HTML endpoint (`https://duckduckgo.com/html/?q=...`) returns a transport error from this machine; unusable as a search path.
- Bing SERPs were heavily polluted for trading-bot queries — the `hummingbot architecture order tracking state reconciliation` query returned only unrelated POS/login pages, and `jesse trade framework docs live mode backtest "same code" route strategy` returned Chinese name-meaning sites. Bing is only usable when the query contains a distinctive site-scoped token (e.g. `freqtrade docs ...`).
- Bing query `"freqtrade" startup reconcile open orders exchange "handle_onexchange_order" OR "reconciliation"` returned only generic homepage/aggregator hits (freqtrade.cn, zhihu, csdn) — no primary source surfaced. Freqtrade's startup-reconciliation internals (`handle_onexchange_order` in `persistence/trade_model.py`) are undocumented in the official docs and were not retrieved.
- `https://hummingbot.org/client/kill-switch/` returns 404 (page exists in the nav as "Kill Switch" but the URL is not at that path) — Hummingbot's kill-switch / balance-limit risk features remain unverified.
- OctoBot's GitHub README is almost entirely marketing (install methods, strategy-mode marketing pages, sponsor list) and yielded no architectural or engineering detail; its engineering claims could not be sourced from a primary doc in the budget available. OctoBot is effectively uncovered by this angle.
- Hummingbot's `Connectors` overview page is a governance/maintenance overview (bounties, HGP proposals, HBOT voting) with no order-tracking or rate-limit mechanics; the per-connector "Building CLOB Connectors" page was not fetched.
- Hummingbot's "Troubleshooting" page contains no dedicated "exchange disconnected / state drift" section — its value here is only as incidental evidence of the internal `_order_tracker` API and the WS retry log line.
- Freqtrade's "Trade Object" and "Plugins" docs do not describe what happens to an in-flight `Trade` when the process is killed mid-order; process-crash recovery semantics were not sourced.
